# ADR 0006: Payments module (BC-03 Payment Intent & Lifecycle)

- Status: **PROPOSED**; built for owner review on 2026-11-16 (Module 2). Not deployed.
- Specs: 06-01 (lifecycle, authoritative), 04-02 (payments API), 04-08 (idempotency), 04-06 (events), 02-07 (unknown outcomes), 03-03 §3–4 (placement)
- Builds on: ADR 0001, ADR 0002, ADR 0005 (Module 1, approved baseline `fdce54f`)
- Related: OPEN_QUESTIONS Q1, Q26–Q28, Q29–Q34

## 1. Scope

**Built:** payment intents. Create (with a vault token), confirm, manual capture, cancel or void, expiry, and every 06-01 §5 transition driven by normalized provider observations, with unknown-outcome handling, recovery escalation, audit, events and the private command API.

**Not built (deliberately):**

| Item | Why |
|---|---|
| Refunds (06-01 §8.3) | Separate aggregate whose confirmation feeds BC-05 Ledger, which is not approved yet |
| Partial and multiple capture | Pilot default disables them (06-01 §7.4, PI-028); capture must equal the full authorization |
| Disputes and chargebacks | Separate evidence process (06-01 §8.4) |
| Provider dispatch, webhooks, inquiry | BC-04 Provider Connectivity owns them (03-03 §3); Payments emits commands and consumes normalized observations only |
| Merchant webhooks, receipts | BC-09 |
| Mounting the HTTP API in `cmd/execution` | The D1→D2 service authentication does not exist (M4). An unauthenticated payment API must not run (§7) |

## 2. Placement

BC-03 lives in deployable D2 `execution` (03-03 §3), schema `payment`, runtime role `zp_execution`; the relay uses `zp_relay`. Migrations live in `db/migrations/payment/`:

- `00001_platform_tables.sql` is generated by `cmd/migrate scaffold` (ADR 0005 §4.2);
- `00002_payment_core.sql` holds the core payment tables.

## 3. Reducer (06-01 §5 "the ONLY state mutation authority")

`internal/payment/domain` is pure: it has no I/O, enforced by `internal/archtest`. Commands (`Create`, `Confirm`, `Capture`, `Cancel`, `Expire`) and `Observe` return a `Decision`: steps, the next aggregate, a new operation, a resolution, events and a recovery case. **Each step is one aggregate version and one audit row.**

Decisions taken from the specs, not invented:

- **Create.** The pilot profile requires the token at creation (04-02 §6.1), so `CREATE` and `ATTACH_TOKEN` (06-01 §5.1) apply in one transaction, ending in `REQUIRES_CONFIRMATION`. After a retryable decline, a new token arrives with a newly keyed confirm (trace T4).
- **Unknown.** Unknown is never failure: `PROCESSING` plus resolution `UNKNOWN` plus `payment.outcome.unknown.v1`. New effects stay blocked until verified evidence arrives (PI-INV-05).
- **Cancel.** Before dispatch, the intent is canceled at once. In flight, the request is recorded and the intent stays put; an authorization then queues a void (06-01 §5.1 "queue verified void"), and a no-effect proof leads to `CANCELED`. Once authorized, cancel means a void, and capture-versus-void races resolve as inquiry first. Once succeeded, cancel is refused (use a refund).
- **Evidence must match exactly.** Partial authorization and capture are disabled, so a different amount or currency is a **conflict**: the operation becomes `CONFLICTED`, the intent is frozen and a case opens.
- **Late and duplicate evidence.**
  - A late duplicate is recorded as `DUPLICATE`.
  - A contradiction is a conflict (PI-INV-09, PI-AT-031).
  - An observation for the wrong operation, the wrong kind, an unknown outcome value or the wrong provider account is `QUARANTINED` with a case (PI-AT-032).
- **Expiry.** Applies before confirmation. While in flight it only flags the intent and opens a case; it never terminates an unresolved effect (PI-AT-015). Authorization expiry needs provider proof (`AUTH_EXPIRED_UNCAPTURED`).

## 4. Persistence and database guards

One tenant transaction per command or observation (PI-INV-07). The sequence:

1. Lock the intent row.
2. Run the reducer.
3. Create the operation and attempt, with a stable `provider_instruction_key` (R0).
4. Update the intent with a CAS on `aggregate_version`.
5. Write the transition audit and the outbox events.
6. Open a recovery case if needed.

There is no network call inside the transaction.

The database enforces the invariants again, so the guarantees hold even if application code is wrong:

| Guarantee | Mechanism |
|---|---|
| One unresolved effect per intent (PI-INV-03) | partial unique index on `payment_operations(intent_id)` |
| Terminal status never changes; `SUCCEEDED` only from executing states; captured and authorized never decrease; version +1 per update; identity and amount immutable | trigger `zp_intent_guard` |
| Proven operation outcome cannot be rewritten (only `CONFLICTED`) | trigger `zp_operation_guard` |
| Stable provider instruction identity; one instruction per provider account | trigger + unique indexes |
| Manual capture cannot exceed authorization; `SUCCEEDED` ⇒ captured > 0; terminal ⇒ no active operation | `CHECK` constraints |
| History append-only (transitions, observations, command log) | triggers; no `UPDATE`/`DELETE` grants |
| Nothing deleted, even by the owner | triggers on every table |
| Tenant isolation | forced RLS on every tenant table |
| Least privilege | `zp_execution`: `SELECT`, `INSERT`, column-level `UPDATE`; no `DELETE` |

## 5. Idempotency, events, inbox

- Every POST goes through the Module 1 registry: scope = environment, cell, legal entity, tenant, merchant, client, principal, API major, route, operation. Replays return the stored resource; a changed payload gets 422 with zero effect; concurrent first submissions serialize on the key.
- **Events (04-06 registry names only):** `payment.intent.created`, `payment.attempt.requested` (the command to BC-04, with `operation_kind` CONFIRM, CAPTURE or VOID), `payment.authorization.confirmed`, `payment.capture.confirmed` (carries `economic_effect_id` for BC-05) and `payment.outcome.unknown`. Schemas live in `api/events/payment/`. Terminal failure, cancel and expiry have no registry event (Q30); they are in the audit.
- **Consumed:** `provider.outcome.observed.v1` and `payment.attempt.dispatched.v1`, via the inbox (consumer `payment.reducer`), with a second dedupe on `observation_id` (PI-AT-029). Unknown types or majors, or a missing scope, are refused so the relay parks them (PI-AT-049, -052).

## 6. Recovery and scheduling

- `EscalateUnresolved(horizon)` opens an `UNRESOLVED_OPERATION` case for operations still `PENDING` or `UNKNOWN` after the horizon. It never resolves, fails or retries anything (06-01 §7.3 R5, PI-046). The horizon must be configured; none is invented (Q32).
- `ExpireDue` applies business expiry.
- **Cross-tenant scheduling without weakening RLS.** `payment.work_schedule` holds only identifiers: kind, internal ID, tenant, environment, cell, legal entity and due time. It has no amounts, references or PII. Sweepers read due identifiers there and act inside each tenant's own RLS transaction.
- `payment.recovery_cases` holds one open case per intent, operation and reason. Cases are resolved by an approved recovery process, not by the runtime role.

## 7. API

- `api/openapi/execution.v1.yaml` is the private D1→D2 command API (03-03 §4 `payment-command-api`), covering the 04-02 payment-intent paths and `GET /v1/operations/{id}`. Code is generated with oapi-codegen into `internal/apigen/executionapi`; the adapter is `internal/payment/http`.
- **Wire format:** decimal-string amounts (ADR 0001 §3; Q1) and lower-case enums (ADR 0001 §2; Q29). Bodies are strict (`additionalProperties: false`, unknown fields refused), and every POST requires `Idempotency-Key` (`test/contract`). Errors are RFC 9457. Nothing internal is exposed: no token, provider account, policy or tenant.
- **Authentication:** `Handler` requires an `Authenticator` that derives the scope from verified caller claims; without one, every request gets 401. **It is not mounted in `cmd/execution`** until the D1→D2 service identity exists (M4, Q34).

## 8. Ports to other modules

- `Eligibility` (BC-02 enforcement) is called at each effect point (create, confirm, capture) outside the transaction. A denial gives `capability_not_available`; an outage gives `temporarily_unavailable`. It fails closed (PI-015, PI-AT-061). Cancel is not blocked by an outage, because it only reduces exposure.
- `TokenVault` validates token references at the vault boundary (04-02 §5.2). Only the reference is stored (PI-004). `merchant_reference` refuses anything that passes a Luhn check like a card number (PI-AT-008).

## 9. Consequences

- BC-04 can be built against `payment.attempt.requested.v1` and must emit `provider.outcome.observed.v1` with the 06-01 normalized outcome names.
- BC-05 Ledger can post from `payment.capture.confirmed.v1`, keyed by `economic_effect_id`.
- Refunds, the D1→D2 authentication and the connector are the next prerequisites for a pilot.
